# Assignment 33: Chat with SQL Database using LangChain

An AI Data Assistant that lets business users ask questions in plain English,
generates SQL dynamically with an LLM, runs it safely and returns the answer.
Stack: LangChain, SQLAlchemy, SQLite, MySQL Workbench (MySQL Server).

## Project structure
| File | Purpose |
|------|---------|
| `part1_create_sqlite.py` | Part 1 – creates `company.db`, tables, 12 employees + 12 sales, verification queries |
| `part2_langchain_engine.py` | Part 2 – SQLAlchemy engine + `SQLDatabase.from_uri("sqlite:///company.db")` |
| `mysql_setup.sql` | Part 3 – run in MySQL Workbench to create `company_db` with the same data |
| `part3_mysql_workbench.py` | Part 3 – connects code to the Workbench database (`--setup` creates it from code) |
| `sql_agent.py` | Part 4 – SQL toolkit, SQL agent, chat (Tasks 5–8) |
| `config.py` | DB URIs and LLM factory (OpenAI / Groq / Ollama) |
| `.env.example` | Copy to `.env` and fill in keys / MySQL password |

## How to run
```bash
pip install -r requirements.txt

python part1_create_sqlite.py   # Part 1
```

## Database schema
- `employees(id PK, name, department, salary)`
- `sales(sale_id PK, employee_id, amount, sale_date)`

## Restrictions followed
Only LangChain, SQLAlchemy, SQLite and Workbench are used. No SQL is hardcoded
in the agent; every query is generated by the LLM. The only fixed SQL is the
setup/verification SQL for creating and checking the sample data (Parts 1–3).

## Safety design
- SQLite agent connection is **read-only** (`mode=ro`) – a DELETE/UPDATE fails at database level (tested).
- System prompt forbids INSERT/UPDATE/DELETE/DROP/ALTER and caps rows (`top_k=10`).
- Toolkit includes the query-checker tool so the LLM re-validates SQL before running.
- For MySQL, use a dedicated user with only `SELECT` privilege.

## Task 8 – Handling ambiguous queries
Questions like "Show me the data", "Who is the best employee?" or "How are we doing?"
are vague. Because of the system prompt, the agent asks a clarifying question
(e.g. "Best by salary or by total sales? Which table?") instead of guessing,
or inspects the schema and offers the possible interpretations.
Without such a prompt, agents tend to guess a metric and may give a misleading answer.

## Observations & Short Answers

**1. Why are SQL agents better than manual SQL generation?**
A manual chain generates one query in a fixed flow. An agent reasons in a loop:
it lists tables, reads the schema, writes SQL, checks it, runs it, sees an error
or odd result, and corrects itself. It chooses tools on its own, handles multi-step
questions and recovers from mistakes, so business users get more reliable answers
without knowing SQL.

**2. Difference between SQL agents and RAG?**
RAG retrieves relevant text chunks (usually from a vector store of unstructured
documents) and gives them to the LLM as context. A SQL agent queries structured
data live, so it can compute exact aggregates (SUM, AVG, GROUP BY) and the data is
always current. RAG is good for documents and meaning-based lookup; SQL agents are
good for precise, numeric, relational questions.

**3. Risks of allowing unrestricted SQL access?**
- Destructive queries (DROP/DELETE/UPDATE) from mistakes or prompt injection.
- Data leakage – exposure of sensitive columns such as salaries or personal data.
- SQL injection via malicious user input steering the LLM.
- Expensive queries (huge joins, no LIMIT) that slow or crash the database.
- Wrong or hallucinated queries leading to wrong business decisions.

Mitigations: read-only/least-privilege DB users, table allow-lists, row limits,
query checking, logging/auditing, and human approval for any write operation.
